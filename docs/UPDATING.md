# SDK 업데이트

0.3.10은 현재 저장소가 미리 연결된 배포본이며 첫 실행부터 이름 목록을 자동으로 읽습니다. 주소나 ID를 별도로 전달할 필요가 없습니다. 최신 편집기로 게시를 완료하면 자동 등록됩니다. 기존 청크와 ID는 유지되며 구버전으로만 게시한 모델은 한 번 재게시하면 됩니다. 테스트 페이지는 마지막 연결·모델을 기억합니다. SDK 업데이트 완료 후 기존 테스트 서버를 다시 실행하고 페이지를 새로고침하세요.

0.3.9부터는 SDK를 업데이트해 페이지를 다시 열면, 그 후 모델의 새 게시본은 기본 5초 간격 확인으로 자동 반영됩니다. 모델 다운로드·검증 시간과 백그라운드 브라우저 지연이 추가될 수 있습니다. SDK 프로그램 자체는 계속 아래 `update.cmd`로 업데이트합니다. 자동 반영이 완료되기 전이나 구버전/고정 게시본을 사용하는 화면에는 이전 게시본 삭제가 영향을 줄 수 있습니다.

## 한 번 클릭으로 업데이트

SDK0.3.5부터 **SDK 루트의 `update.cmd`**를 실행합니다. 먼저 해당 SDK의 테스트 서버와 개발 서버를 종료하세요. 완료 후 `examples/test-server.cmd`를 다시 실행하고 브라우저를 새로 고칩니다. 테스트 서버는 계속 Windows 기본 PowerShell을 사용하며 Node.js·pnpm을 설치하지 않습니다. 업데이트할 때만 인터넷 연결이 필요합니다.

- ZIP 사본: Git 설치 없이 공식 GitHub 저장소에서 최신 main의 고정 커밋 ZIP을 내려받습니다. 크기·경로·SDK manifest SHA256을 모두 검사한 뒤, manifest에 등록된 SDK 파일만 교체합니다.
- Git 사본: 기존 Git 설치를 사용합니다. SDK 전용 저장소인지 확인하고, 같은 고정 커밋을 fetch한 뒤 detached HEAD로 전환합니다. 기존 브랜치·태그는 보존하며 force/reset/clean은 실행하지 않습니다. 개인 파일을 SDK에 추가해 커밋한 사본은 0.3.6부터 변경 전에 중단합니다. 개인 파일은 별도 프로젝트에 보관하고 깨끗한 SDK 사본을 사용하세요. Git 사본에서 Git이 없으면 설치하거나 기존 ZIP 사본을 사용해야 합니다.
- 직접 수정한 SDK 파일이나 새 SDK 경로와 충돌하는 로컬 파일이 있으면 업데이트 전에 중단합니다. `.env`, 사용자 모델, 청크, 개발 설치 결과 같은 등록 외 파일은 전송하거나 덮어쓰지 않습니다. 외부 프로젝트에 설치한 SDK 의존성은 그 프로젝트에서 별도로 버전을 갱신합니다.
- 현재 SDK와 백업은 SDK 폴더 옆의 `.dt-sdk-update-...` 폴더에 보관합니다. 교체 중 오류가 나면 검증된 이전 파일로 복구합니다. 중단된 작업은 다음 실행에서 복구한 뒤 재시도하며, 그 사이 변경한 파일이 발견되면 덮어쓰지 않고 백업 경로를 안내합니다. SDK 폴더 옆에 쓸 수 있는 권한이 필요합니다.
- 이미 최신 커밋이고 설치 파일 해시가 같으면 다시 교체하지 않습니다. 업데이트 성공 이력이 있는 같은 커밋은 ZIP을 다시 내려받지 않습니다. 로컬 SDK보다 낮은 버전으로 자동 변경하지 않습니다.

0.3.4 이하에는 이 CMD가 없으므로 **이번 한 번** 최신 전체 SDK를 받거나, 같은 배포본의 `update.cmd`·`update.ps1` 두 파일을 기존 SDK 루트에 함께 복사합니다. 두 파일이 새 공식 배포본과 동일하면 기존 Git 사본에서도 첫 업데이트를 진행할 수 있습니다. 이후부터는 `update.cmd`만 실행합니다.

### 0.3.6·0.3.7에서 rev-parse 오류가 나는 경우

관리자나 다른 Windows 사용자가 만든 SDK 폴더에서는 Git의 소유자 검사 때문에 업데이트가 중단될 수 있습니다. 기존 파일은 보존됩니다. 0.3.8은 선택한 SDK 경로만 해당 Git 프로세스에서 허용하며 전역 Git 설정은 변경하지 않습니다. 구버전 updater는 스스로 이 오류를 넘을 수 없으므로 이번 한 번 최신 전체 SDK를 새 폴더에 받으세요. 모델·설정은 기존 폴더에 유지하고, 이후 새 SDK의 `update.cmd`를 사용합니다.

## 기존 0.2.x 프로젝트 전환

0.3.0은 API 서버를 제거한 공개 인터페이스 변경입니다. 기존 0.2.x 프로젝트를 자동으로 같은 함수 이름으로 전환하지 않습니다. 청크 데이터 계약과 저장소 원본은 그대로 사용합니다.

1. 현재 외부 프로젝트와 사용자 모델·설정을 보존합니다.
2. 새 SDK를 별도 폴더에 풀고 외부 프로젝트의 의존성을 새 버전으로 변경합니다.
3. DeliveryApiClient/API URL/token 대신 DeliveryClient와 LocalChunkSource 또는 HttpChunkSource를 사용합니다. [API 명세](API.md)를 확인하세요.
4. 테스트 예제는 `examples/test-server.cmd`를 실행합니다. 전체 SDK에 미리 빌드된 페이지가 포함되어 Windows 기본 PowerShell만 필요하며 Node.js·pnpm·시작 시 인터넷 설치는 필요 없습니다. 예제 소스 개발 명령은 `examples/web/README.md`를 참고하세요. 이전 local/remote-server CMD와 API 설정은 새 SDK가 사용하지 않습니다.
5. 로컬 청크의 목록·점진 로딩·선택·스크립트 공개 속성과 오류/취소를 확인합니다.
6. 새 웹페이지 배포 전에 `dispose()`와 이벤트 해제, 실제 사용하는 브라우저의 폴더/CORS/네트워크 권한을 확인합니다.

설치·빌드 결과와 개발자 설정은 공개 SDK 파일 밖에 둡니다. SDK의 불변 파일 해시 검증은 유지하며 pnpm 하드 링크는 설치 후 byte 동일한 파일로 분리합니다. 모델이 바뀌어도 통합레벨 ID를 API JSON에 입력하는 단계는 없습니다.

원격 S3 인증은 서버에 CORS와 임시 인증·정확한 저장소 권한을 준비한 뒤 호스트 source adapter를 연결해야 합니다. 공개 SDK에 장기 접속 키를 넣지 않습니다. 원격 설정을 바꾸거나 Git에 push하는 작업은 로컬 SDK 테스트와 별개입니다.
